## Why this lab matters

Forward kinematics has one answer; inverse kinematics has **zero, one, several or infinitely many** (MR p. 219). A robot controller must therefore (i) know all candidate solutions, (ii) reject those outside the joint limits and (iii) choose one that is safe and close to where the robot is now. Analytic IK gives the complete set quickly but only for special geometries; numerical IK (Newton–Raphson) works for any arm but returns *one* solution — the one whose basin of attraction contains the initial guess (MR p. 227). In this lab you build both, compare them, and use the comparison on two cases:

* **Biomedical — needle-guide positioning for a biopsy.** The course arm with the 0.06 m needle guide (project scenario S3, `desktop_6r`) must align the guide with five needle trajectories on a phantom (`biopsy_targets.csv`, illustrative values). You find all analytic solutions, remove those outside the $\pm165^\circ$ ($\pm175^\circ$ for joint 6) limits, choose the one closest to the ready pose $q_\text{home}$, and check what a plain Newton–Raphson solver would have commanded instead.
* **Defence — EOD manipulator grasp.** For the gripper pose of Workshop Problem 3 (`eod_6r_ugv`, scenario S4) a multi-start numerical search must recover all 8 solutions found by hand and pick the single safe one.

All robot numbers are those of the course robot models (Course resources: Course robot models and hardware safety checklist), copied into `data/robots.json`; geometry is illustrative unless it is a textbook robot.

# Derivation of the course-arm IK

The course arm has the layout of the UR5 of MR Example 4.5 (Week 6): $\hat\omega_1 = \hat z$; $\hat\omega_2 = \hat\omega_3 = \hat\omega_4 = \hat y$ at heights $H_1$; $\hat\omega_5 = -\hat z$ through $(L_1+L_2, W_1, 0)$; $\hat\omega_6 = \hat y$ through $(L_1+L_2, 0, H_1 - H_2)$; $M$ has rotation $R_M = \begin{bmatrix}-1&0&0\\0&0&1\\0&1&0\end{bmatrix}$ and position $(L_1+L_2,\ W_1+W_2,\ H_1-H_2)$. Its wrist axes do **not** meet in one point, so MR's PUMA decoupling does not apply directly — but three geometric facts give a closed form (the same structure as the lecture's subproblem solution, notes WE-A7). Let $T_{sd} = (R, p)$ and $\hat z_b = R\hat e_3$.

1. **Wrist point.** Axis 6 is $\hat z_b$, and axes 5 and 6 meet at $p_5 = p - (W_2 + \ell_\text{tool})\hat z_b$.
2. **Base angle.** Joints 2–4 rotate about axes parallel to $\hat y' = (-\sin\theta_1, \cos\theta_1, 0)$, so they never change the "lateral" coordinate $\hat y'^{\mathsf T}x$ of a point; for axis 5 it is $W_1$: $-\sin\theta_1\,p_{5x} + \cos\theta_1\,p_{5y} = W_1$. With $\rho = \sqrt{p_{5x}^2 + p_{5y}^2}$, $\varphi = \mathrm{atan2}(p_{5y}, p_{5x})$: $\theta_1 = \varphi - \sin^{-1}(W_1/\rho)$ or $\theta_1 = \varphi - \pi + \sin^{-1}(W_1/\rho)$ (two solutions; none if $\rho < W_1$). This is the same equation as the shoulder offset $d_1$ of a PUMA-type arm (MR Fig. 6.3, Practice Problem 3).
3. **Wrist angle 5.** The rotation part of the PoE is $R = \mathrm{Rot}(\hat z,\theta_1)\mathrm{Rot}(\hat y,\theta_{234})\mathrm{Rot}(\hat z,-\theta_5)\mathrm{Rot}(\hat y,\theta_6)R_M$ with $\theta_{234} = \theta_2+\theta_3+\theta_4$. Rotations about $\hat y$ do not change the $\hat y$-row, so the second row of $R' = \mathrm{Rot}(\hat z,-\theta_1)R$ is $(\sin\theta_5\cos\theta_6,\ -\sin\theta_5\sin\theta_6,\ \cos\theta_5)$. Hence $\cos\theta_5 = \hat y'^{\mathsf T}\hat z_b$ and $\theta_5 = \pm\cos^{-1}(\cdot)$ (two solutions).
4. **Wrist angle 6.** $\theta_6 = \mathrm{atan2}\big(-R'_{22}/\sin\theta_5,\ R'_{21}/\sin\theta_5\big)$ (1-based indices). If $\sin\theta_5 = 0$ the axes 4 and 6 are parallel (a wrist singularity): $\theta_6$ is arbitrary; the code sets it to 0.
5. **Sum $\theta_{234}$.** $\mathrm{Rot}(\hat y,\theta_{234}) = R'\big(\mathrm{Rot}(\hat z,-\theta_5)\mathrm{Rot}(\hat y,\theta_6)R_M\big)^{\mathsf T}$, so $\theta_{234} = \mathrm{atan2}(r_{13}, r_{11})$ of that matrix.
6. **Planar 2R.** In the arm plane (coordinates $x', z'$ after $\mathrm{Rot}(\hat z,-\theta_1)$), the joint-4 point is $p_4' = p_5' + H_2(\sin\theta_{234},\ \cdot\ ,\cos\theta_{234})$. With $X = x_4'$ and $Y = H_1 - z_4'$ (positive $\theta_2$ about $+\hat y$ turns the arm down), $X = L_1c_2 + L_2c_{23}$, $Y = L_1s_2 + L_2s_{23}$: use `ik_2r` (two elbows), then $\theta_4 = \theta_{234} - \theta_2 - \theta_3$.

Total: $2\times2\times2 = 8$ candidate solutions; a branch disappears when its 2R target is out of reach.

# Troubleshooting

| Symptom | Likely cause and fix |
|---|---|
| `pk1` gives the right magnitude but the wrong sign | $\mathrm{atan2}(\hat\omega^{\mathsf T}(u'\times v'), \dots)$: the order of the cross product is $u'\times v'$, and $\hat\omega$ must be a unit vector. |
| `pk1` raises `ValueError` on valid data | You forgot to subtract the axis point $r$, or your tolerance is too tight (use $10^{-6}$). |
| `pk2` solutions reproduce $q$ only for one random case in two | Order: $e^{[\xi_1]\theta_1}e^{[\xi_2]\theta_2}p$ — rotate $p$ to $c$ about axis **2**, then $c$ to $q$ about axis **1**. |
| `ik_course_arm` finds the right number of solutions but FK misses by a few cm | Tool length forgotten in step 1 (`desktop_6r` has $W_2 + 0.06$), or the sign of $Y = H_1 - z_4'$. |
| Only 4 solutions where you expect 8 | Often correct: for some $(\theta_1, \theta_5)$ pairs the 2R target is out of reach. Print $\cos\theta_3$ for every branch. |
| `ik_newton_body` differs from `IKinBody` after a few iterations | Same stopping rule: test **before** each update, stop when $\lVert\omega_b\rVert\le\epsilon_\omega$ **and** $\lVert v_b\rVert\le\epsilon_v$, at most `max_iter` updates; use `np.linalg.pinv`. |
| `all_solutions_search` reports $\theta$ and $\theta + 2\pi$ as two solutions | Wrap before comparing (`wrap_to_pi`), and compare the wrapped **difference**, not the values (an angle near $\pm\pi$ wraps to either end). |
| `select_solution` returns `None` although a solution looks feasible | A joint at e.g. $170^\circ$ is outside $\pm165^\circ$ even though $170^\circ - 360^\circ$ is not: check each joint's representatives $\theta_j - 2\pi, \theta_j, \theta_j + 2\pi$. |
| `ModuleNotFoundError: starter` | Run `pytest` from inside your Lab code folder, or set `LAB_IMPL` to your file name without `.py`. |

# Pre-lab answers (released after the session)

1. 0 (inside the hole, $r < 0.2$), 1 (inner boundary, folded), 2, 1 (outer boundary, stretched).
2. $\mathrm{atan2}(-1,-1) = -135^\circ$ (third quadrant); $\tan^{-1}(1) = 45^\circ$. `atan2` uses the signs of both arguments (MR p. 217).
3. $\hat\omega^{\mathsf T}(p - r) = \hat\omega^{\mathsf T}(q - r)$ (same height along the axis) and $\lVert u'\rVert = \lVert v'\rVert$ (same distance from the axis) (MLS Eq. 3.19).
4. $g = \theta^2 - 2$, $g' = 2\theta$: $\theta^1 = 1 - (1-2)/2 = 1.5$, $\theta^2 = 1.5 - 0.25/3 = 1.41667$ (true root 1.41421).
5. $T_{sd} - T_{sb}$ is not a twist: the pseudoinverse of $J_b$ must act on a body twist. $\log(T_{sb}^{-1}T_{sd})$ is the body twist that moves $\{b\}$ to the goal in unit time (MR p. 228).

**Random starts (Checkpoint 4).** C++ cannot reproduce NumPy's random generator, so `all_solutions_search` takes the initial guesses as a matrix `starts` ($n_\text{starts}\times n$, one start per row) instead of `n_starts` and `seed`. The tests pass the 200 starts of `np.random.default_rng(0)` stored in `cpp_cases.json` (the 20-start case uses their first 20 rows), so the 200-start results (8 solutions at P8, 4 at $q_\text{home}$) are those of the Python track. The 20-start count is only printed (`./build/lab_tests -s -tc="*all_solutions*"`), not checked as "fewer than 8": some starts lie close to a singularity (e.g. an almost stretched elbow), so their first Newton step through the nearly singular $J_b$ is huge, and which branch they end on depends on round-off (Eigen's SVD vs NumPy's LAPACK) — with the same 20 starts the C++ reference finds all 8 branches where Python finds 6. This is itself a result worth one sentence in your reflection on "how many starts are enough". For the results-sheet plot (5–200 starts, three seeds) use `lab::random_starts(n_starts, 6, seed)` (C++ `std::mt19937`, the same numbers on every compiler; they differ from NumPy's, so your counts will differ slightly from a Python classmate's), or read the NumPy starts from `cpp_cases.json` (key `all_solutions_search_finds_analytic_set`, field `starts`).

**Differences from the Python version.**

| Python | C++ |
|---|---|
| `Slist`, `Blist`, joint vectors, `limits`: NumPy arrays | `Eigen::MatrixXd` $6\times n$ (one axis per column), `Eigen::VectorXd`, `Eigen::MatrixXd` $n\times2$ |
| `load_robot(name)` returns `(Slist, M, info)` | returns a `lab::Robot` with fields `Slist`, `M`, `name`, `joint_types`, `limits`, `q_home`, `has_geometry`, `geometry` |
| `info["geometry"]` (dict with `W1`, …, `tool`) | `lab::Geometry` with the same field names (`robot.geometry`) |
| `load_biopsy_targets()`: list of dicts | `std::vector<lab::BiopsyTarget>` with fields `id`, `entry`, `axis`, `note` |
| `pk1` raises `ValueError` | `throw std::invalid_argument(...)`; in `pk2`, skip a $\gamma$ with `catch (const std::invalid_argument&)` |
| `pk2`, `ik_2r` return lists of tuples; `pk3` a list of angles | `std::vector<std::pair<double, double>>` (`.first` = $\theta_1$, `.second` = $\theta_2$); `std::vector<double>` |
| `ik_course_arm(T, geom)` returns a list of arrays | `std::vector<Eigen::VectorXd>` (6 entries each) |
| `newton_raphson(g, dg, theta0, ...)` with `g`, `dg` any callables, scalar or vector | `lab::ResidualFunction` / `lab::JacobianFunction` (`std::function`, pass lambdas); a scalar problem uses vectors of length 1; returns `lab::NewtonResult{theta, history}`, each step `{k, theta, g}` |
| `ik_newton_body` / `ik_newton_space` return `(theta, success, table)`, rows `{i, theta, V_b or V_s, w_err, v_err}` | `lab::IKTableResult{theta, success, table}`, rows `lab::IKRow{i, theta, V, w_err, v_err}` (`V` is $\mathcal V_b$ or $\mathcal V_s$) |
| `all_solutions_search(Slist, M, T_sd, n_starts, seed, ...)` returns `(solutions, counts, n_converged)` | `all_solutions_search(Slist, M, T_sd, starts, ...)` (see above) returns `lab::SearchResult{solutions, counts, n_converged}` |
| `select_solution` returns an array or `None` | `std::optional<Eigen::VectorXd>`: `if (best) use(*best);`, `return std::nullopt;` |
| `np.linalg.pinv`, `np.linalg.solve`, `np.clip`, `np.pi` | `lab::pinv` (given), `A.partialPivLu().solve(b)`, `std::clamp(x, lo, hi)`, a local `constexpr double PI = 3.14159265358979323846;` |
| results-sheet plots (matplotlib) | write the numbers as CSV (`sbeg::write_csv` from `<sbeg/labio.hpp>`) in a small `experiments.cpp` of your own and plot them with a short Python script; the results-sheet requirements do not change |

A matrix-size mistake (e.g. multiplying a $6\times6$ matrix by a 3-vector) does not crash the test program: it is reported as a failed test with the message "Eigen: wrong matrix size or index out of range".

**C++ troubleshooting.**

| Symptom | Likely cause | Fix |
|---|---|---|
| `cpp_support not found` | the course folder `cpp_support` is not next to / above your Lab code folder | copy it there, or configure with `-DSBEG_CPP_SUPPORT=<path>` |
| `No CMAKE_CXX_COMPILER could be found` | no C++ compiler installed | install it (see Requirements); on Windows run from the "x64 Native Tools Command Prompt" if Ninja cannot find `cl` |
| `cannot open file: .../cpp_cases.json` | Lab code folder moved after configuring | delete the `build` folder and configure again |
| `test_pk1_no_solution` fails with "threw a DIFFERENT exception" | wrong exception type | `throw std::invalid_argument(...)`, not `std::runtime_error` or `std::logic_error` |
| `pk2` stops the test with an exception | the `pk1` exception of an invalid $\gamma$ is not caught | `try { ... } catch (const std::invalid_argument&) { continue; }` around the two `pk1` calls |
| `wrap_to_pi` of your own gives values in $[-3\pi, \pi)$ | `std::fmod` keeps the sign of the dividend (Python's `%` does not) | use the given `wrap_to_pi`, or add $2\pi$ when the remainder is negative |
| `ik_newton_body` differs from `mr::ikin_body` after a few iterations | stopping test after the update, or "and" / "or" swapped in the stopping rule | test before each update; continue while $\lVert\omega_b\rVert>\epsilon_\omega$ **or** $\lVert v_b\rVert>\epsilon_v$ (as in Python) |
| Wrong results only after `auto V = A * B;` | `auto` keeps an Eigen expression, not a matrix | write the type: `sbeg::Vector6d V = A * B;` |
| Tests still show your old result | program not rebuilt | `cmake --build build` before `./build/lab_tests` |
